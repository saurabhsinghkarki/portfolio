Background 1440 × 320
01 · Context

A booking form that vanished the moment it mattered

Polo Hotels' booking engine lets guests search by destination, check-in and check-out dates, guest count, room count and a promo code. Once they hit Search, they land on the Hotel Listing Page — and the form disappears entirely.

If a guest wanted to shift their trip by a day, add a room, or try a promo code after seeing prices, the only path was back. Back to the homepage. Re-enter every field. Search again. What should have been a two-second edit became a five-step detour.

What the booking-engine leaders already knew

I audited five booking platforms guests already trust, watching specifically for what happens to the search form after results load.

Persistent search is table stakes

Four of five platforms keep some form of the search bar reachable at all times. Polo's disappearing form was the outlier, not the norm.

Editing dates shouldn't reload the world

The strongest experiences (Booking.com, Airbnb, Expedia) update results in place. Hilton's full reload was the closest analogue to Polo's break-and-restart pattern.

Mobile needs its own shape

Nobody shrinks the desktop bar onto mobile untouched — it collapses into a single tappable summary, expanding into a focused editor only on demand.

Designing for the guest doing the comparing

Meera Anand

34 · Marketing Director · Bengaluru

"I usually have four tabs open comparing the same weekend. If I have to restart a search because I moved a date by one day, I've probably already left for a competitor's tab."

Behaviour

  • Books 8–10 stays a year, mixing work trips and family holidays
  • Compares 3–4 properties before committing
  • Books primarily on mobile during commute or lunch breaks

Goals

  • Adjust dates and room count without losing her place
  • Apply a promo code after she's already seen prices
  • Get to payment in as few screens as possible

Frustrations

  • Re-entering the same search twice in one session
  • Losing scroll position after navigating back
  • Forms that behave differently on mobile than desktop

Solution 1440 × 440
05 · The Solution

A booking widget that never leaves the page

I designed a sticky booking widget docked to the top of the Hotel Listing Page. Destination, check-in, check-out, guests, rooms and promo code are all editable in place — updating results instantly instead of sending the guest back to start over.

Why a docked widget, not a modal

A modal would still interrupt — it demands full attention and blocks the results underneath. Docking the widget to the top keeps the listing visible at all times, so a date change feels like a refinement of what's already on screen, not a departure from it.

Design Decisions 1440 × 460
06 · Design Decisions

Every choice, and the reasoning behind it

01

Persistent search

The widget is docked, not dismissible — search stays exactly as reachable as the results it's filtering.

02

Reduced cognitive load

Collapsed by default to a single readable summary line, so the guest reads results first, form second.

03

Maintain context

Editing never navigates away — the results grid updates beneath the widget, preserving scroll and selection.

04

Responsive layout

Desktop shows all fields in a row; mobile collapses to a tappable summary chip that opens a focused sheet.

05

Accessibility

Every field is a native, labelled control — reachable and operable with a keyboard alone, with visible focus.

06

Fast refinement

Changes apply the moment a field is confirmed — no separate "search again" step required.

07

Progressive disclosure

Guests & rooms and promo code sit one tap deeper, so rarely-touched fields don't compete for attention.

Learnings 1440 × 360
10 · Key Learnings

What this project reinforced

This project was a reminder that product thinking often means removing a step, not adding a feature. Nothing about the sticky widget was novel — every competitor in the research already had some version of it. The work was in fitting it to Polo's existing information architecture without disrupting the booking team's roadmap for the quarter.

Designing for a high-intent user like Meera meant optimising for speed over guidance — she already knows what she wants; the interface's job is to stay out of her way. Balancing that against the business goal of surfacing promo codes and upsells meant keeping those fields present but never blocking the primary task of finding a room.

Building the front end myself changed how I designed the widget's states. Knowing exactly how an input[type="date"] behaves across browsers, or how a stepper control needs to announce its value to a screen reader, shaped decisions earlier than a handoff-only process would have allowed.
